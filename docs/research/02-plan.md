# Work plan

Ordered so that each phase produces something publishable on its own, and so
that the riskiest assumption is tested first. Nothing here depends on rewriting
the paper; that happens last, once there are results to write about.

## Phase 1 — Build CHIRON-BUGS (the contribution)

This is the risky phase and the valuable one. Everything else is support.

### 1.1 Inventory
Reconstruct each bug from the memory notes + `git log` into a uniform record:

```
bugs/<id>/
  README.md      root cause, the faulting event, why it escaped which oracle
  revert.patch   the minimal change that reintroduces the bug
  repro/         the minimal multi-hart program that activates it
  meta.yaml      class, subsystem, fix commit, activation cycle, harts involved
```

Candidate seeds already documented and fixed (~20; each must be re-verified,
several may collapse into one root cause or fail to reproduce in isolation):
ACE `responseBuffer` squash clobber · dual-Unique line coherence violation ·
stale `CleanUnique` upgrade · word-granular snoop kill / LR-SC forward progress ·
D-cache arbiter atomic lockout · CCU snoop starvation · ROB coherent-squash
livelock · `robFifo` out-of-window rollback · speculative MMIO never squashed ·
scheduler `releasedBuffer` mask bug · divider `mExtensionReady` last-connect ·
M-extension shared response port · L2 MSHR write-miss refill corruption ·
D-cache `reqSched` silent drop · illegal-instruction trap absence ·
CCU/L2 cold-I-fetch deadlock.

**The honest risk, stated up front:** some of these will not revert cleanly on
today's `main`, and some will turn out to be the same defect seen twice. A
corpus of 12 solid, independently reproducible bugs is worth far more than 20
shaky ones. Report the attrition — reviewers trust a paper that says "we started
with 20 and 13 survived isolation."

### 1.2 The measurement harness
One driver that, for each bug × each technique, records: detected (y/n),
detection cycle, faulting cycle, localization output, wall-clock cost. Techniques:
`riscv-tests` · benchmark result check · single-hart lockstep (**the
DiffTest-equivalent baseline — this is the comparison R1 demanded**) ·
quad-hart lockstep · `ci-check` invariants · `ci-smp` micros · litmus ·
stress-sweep · Linux boot.

### 1.3 Determine the faulting cycle
Detection latency is meaningless without a ground-truth "when did it go wrong".
For most of these the reverted RTL is deterministic, so the reference is the
first cycle at which reverted and fixed builds diverge in *any* observed signal
— a bisect over a cycle-by-cycle state hash. This needs building; it is the one
genuinely new piece of infrastructure in Phase 1.

### 1.4 Build the new oracle layers (`03-the-idea.md`)
The mechanism the corpus is used to evaluate. Built **on top of** the existing
lockstep, which stays as the architectural backstop and supplies the reference
values the new layers compare against.

- [ ] **Layer 1 — shadow coherence directory.** Reconstruct per-line ownership
      and state in the golden model from the RTL's observed ACE transactions;
      check **SWMR** and the **data-value invariant** every cycle. Targets the
      dual-Unique, stale-`CleanUnique`, and word-granular-snoop-kill classes.
- [ ] **Layer 2 — slot-ownership tracking.** Tag every ROB/PRF slot with its
      allocating instruction and check each completion against that tag at the
      write port. Closes the reallocated-slot class that recurred four times.
- [ ] **Layer 3 — RVWMO conformance** (shared with Phase 2).

### 1.5 Hunt for new bugs — **do not defer this**
Run the new oracle on stress, litmus, and the Linux boot and record anything it
catches that no existing gate did. One or two previously-unknown bugs converts
the paper from "we measured a thing" to "we measured a thing and it worked."
This is the highest-value experiment in the plan and the one most likely to be
squeezed out by the deadline, so schedule it early.

**Exit criterion:** a table of N real bugs × 8 techniques, with detection
latency in cycles. That table *is* the paper.

## Phase 2 — Standard workloads and cross-processor comparison

Answers B3 and B4. Independent of Phase 1; can run in parallel.

- [ ] **CoreMark + Dhrystone** — port to bare metal and to nommu Linux. Gives
      CoreMark/MHz, the one number every open core publishes.
- [ ] **Embench-IoT** — integer, small, standard.
- [ ] **Splash-3 integer kernels** (`radix` first) — the suite Culsans and
      OpenPiton report, so the multicore comparison is apples-to-apples.
- [ ] **RVWMO litmus tests** on RTL — from `litmus-tests/litmus-tests-riscv`,
      checked against the `model-results/` outcomes shipped in that repo (no
      herdtools/OCaml install needed). Doubles as oracle Layer 3 and as a
      Phase-1 detection technique.
- [ ] Comparison table vs BOOM/SonicBOOM, CVA6(+Culsans), OpenPiton, Rocket,
      C910 — from published numbers where re-running is infeasible, clearly
      marked as such.

**Constraint to respect:** RV64IMA, no F/D. Anything needing floating point is
out unless soft-float cost is acknowledged. Do not plan around FP kernels.

## Phase 3 — Composability, priced (answers B2 / R3)

- [ ] **Demonstrate a real module swap** with no neighbour edits: BTB-only vs
      TAGE front end, and one more substantial swap (replacement policy, or an
      interconnect FSM). Report diff size, files touched, and the IPC delta.
- [ ] **Price the handshake.** R3's claim that ready/fire adds unnecessary
      latency is *correct* and we have the evidence: dead handshake states in
      the CCU cost 4 cycles/beat, and removing them was worth 2.35× on the Linux
      boot. Report the tax honestly as a measured cost of composability, with
      the mitigation.
- [ ] **A small DSE sweep** over the knobs already in `configuration.scala`
      (`branchMaskWidth`, `robAddrWidth`, TAGE/RAS on/off), including the result
      that **branch-mask width, not ROB depth, limits MLP — and widening it
      livelocks `mt-llist`.** Correctness-constrained DSE is a better story than
      an IPC sweep, and it ties Phase 3 back to Phase 1.

---

## Phase 4 — Write

Only after Phases 1–3 have numbers. Reframe from *"we built a composable OoO
multicore with lockstep verification"* to *"here is what actually breaks in a
speculative coherent multicore, why the standard oracle misses it, and the
evidence."* The processor becomes the instrument, not the claim.

## Decisions taken (2026-09-05)

- **Direction:** bug-corpus paper, with the **lockstep mechanism retained and
  extended, not replaced** — it stays the foundation the new oracle layers are
  built on. See `03-the-idea.md`.
- **Venue:** **DAC 2027**, deadline ~mid-November 2026 (DAC 2026 closed
  2025-11-18, DAC 2025 closed 2024-11-19; DAC 2027 not yet officially posted —
  *re-check the official CFP before committing the schedule*). ~10 weeks.
  Fallback: extend to TCAD / TODAES rather than chase the next conference.
- **Downloads approved**, sizes measured via the GitHub API before fetching:

  | repo | size | needed for |
  |---|---|---|
  | `litmus-tests/litmus-tests-riscv` | **3.9 MB** | RVWMO conformance (Layer 3) |
  | `eembc/coremark` | **0.5 MB** | CoreMark/MHz cross-core comparison |
  | `embench/embench-iot` | **1.6 MB** | standard integer workload |
  | `SakalisC/Splash-3` | **13.4 MB** | multicore comparison vs Culsans/OpenPiton |
  | *(Dhrystone)* | ~0.1 MB | classic comparison point |
  | ~~`herd/herdtools7`~~ | ~~60 MB + OCaml toolchain~~ | **not needed** |

  **~19 MB total.** herdtools7 is avoided because `litmus-tests-riscv` ships
  `model-results/` — the precomputed axiomatic outcomes are enough to check RTL
  outcomes against the model. Only build herd7 if we need to author *new* litmus
  tests, and ask first.

  Everything lands outside the repo (or under an ignored path); nothing is
  vendored into `chiron`.
- **Compute:** long runs are allowed but **ask before starting one**. Multi-hour
  jobs (Linux boots, full sweeps, the per-bug measurement matrix) are night
  work — batch them and propose them as a set rather than one at a time.
- **FPGA:** not confirmed available. Plan assumes simulation-only results; the
  synthesis/utilization fix (A5) is parked until board access is confirmed.
